# Latency optimization, prototype 0.0.2

The revised prototype is faster, but still does not meet the 150 ms p95 target.

## Comparison

The saved 0.0.1 VSIX and the revised implementation were run sequentially against the same current 100-page corpus on this Windows/WSL machine. Each fresh session completed initial loading before 36 ordinary edits: six text and six math edits on pages 100, 50, and 1. Both runs measured input through image decoding, the selection layer, and two animation-frame callbacks. No correctness builds ran alongside these measurements.

| Measurement | Original package | Revised implementation |
|---|---:|---:|
| Median ordinary edit | 255 ms | 213.5 ms |
| p95 ordinary edit | 305 ms | 251 ms |
| Maximum ordinary edit | 306 ms | 271 ms |
| Immediate scroll from page 1 to page 2 | 333 ms | 248 ms |
| Immediate jump to page 100 after early edits | 6,822 ms | 5,801 ms |

This comparison shows a 16% median reduction and an 18% p95 reduction. Raw data: [original package](../results/latency-original-comparison.json), [revised build](../results/browser-latency.json).

Other user processes were using substantial CPU during this comparison; they were left running. See [process-load sample](../results/latency-process-load.json) and [machine and source versions](../results/environment.json). These results should not be compared directly with the earlier, less-loaded 177/277 ms median/p95 delivery run. Its raw data remains in [browser-latency-before.json](../results/browser-latency-before.json). This is a small, sequential comparison on a shared machine, not a controlled performance guarantee.

## Changes

- The existing corpus-specific warm-up box is now written as an unused PDF form before retaining the first compiler checkpoint. This retains lazy PDF font initialization as well as TeX initialization. In the smaller diagnostic loop, first-page compiler time fell from roughly 90–100 ms to 67–73 ms. No warm-up content is placed on a document page. This remains specific to the known corpus.
- Glyph provenance uses shipout closures and one buffered sidecar write per page, preserving actual glyph-output order.
- The browser waits for event delivery instead of repeatedly polling an empty queue. Complete frames use compact region/character arrays; the viewer reconstructs the same navigation objects. A bounded event history avoids retaining every rendered revision indefinitely. VS Code uses the same compact frame format.
- PNG encoding uses lossless, unfiltered RGB scanlines. The measured test page shrank from about 163 KB to 117 KB; decoded pixels are identical.
- Idle convergence now builds and retains a complete set of compiler checkpoints. A completed candidate is adopted by the service thread before its next request, only when its source buffers still match. A stale background result is discarded. Previously, convergence refreshed the PDF but left the active compiler's later checkpoints invalidated.
- Checkpoint restoration recovers a saved output prefix if TeX deleted the partial PDF after a fatal error. This is necessary when font resources have already been written before the first checkpoint, and also fixes recovery at later checkpoints.

The new browser regression edits page 1, waits for convergence, then edits page 100. It verifies that compilation resumes at checkpoint 100 and the new text appears within 500 ms. The actual measurement is recorded as `afterConvergenceEdit` in [browser.json](../results/browser.json). This removes the earlier multi-second prefix replay **after idle convergence**. An immediate far jump before convergence still needs sequential replay, as the table shows.

## Validation and remaining cost

The instrumented and reference builds have identical pixels and text on all 100 pages, and the delivered PNG decodes to the renderer's exact RGB pixels. Incremental/full comparisons pass after math edits, rotated TikZ text, first-page reflow, and a fatal error at page 50. Preamble rebuilds update all 100 macro invocations. Fifteen browser interaction checks cover token navigation, selection, stale-output guards, typing/caret stability, error recovery, convergence, and far-page checkpoint reuse.

Compiler resume/layout/PDF finalization still dominates ordinary edits. Under the comparison load, median compiler work was about 99 ms on page 1 and 122–125 ms on pages 50/100, before rendering and browser display. Reaching the full target needs further compiler/output-path work; reducing polling alone cannot achieve it. Fully native Windows checkpointing and general-document rollback remain unimplemented.

Reproduce using `python scripts/benchmark_browser.py http://127.0.0.1:8765 --assert-target`. It intentionally exits with a failure while p95 remains at or above 150 ms. For the smaller diagnostic loop, add `--pages 1 --repeats 3 --output latency-profile.json`.
